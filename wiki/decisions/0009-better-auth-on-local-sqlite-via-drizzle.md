# ADR-0009: Better Auth, persisted on local SQLite through Drizzle, rebound to D1 at Cluster D

- **Status:** Accepted. Timing amended by [ADR-0015](./0015-one-database-driver-d1-everywhere.md): the D1 swap happened at Cluster C, not D
- **Date:** 2026-09-22
- **Deciders:** AI (backend), pending human review
- **Requirement:** `REQ-B.5`, `REQ-B.2`, `REQ-D.1`, `REQ-M.2`

## Context

`REQ-B.5` puts authentication in Cluster B and is explicit about *how*: drop in a
library as a **black box** — `getSession()` and route gating only. The course
adds that EdgeLedger's Workers-native auth (Web Crypto hashing, sessions in KV)
is *afterwards reading*, not a pattern to copy ([ADR-0003](./0003-edgeledger-is-comparison-not-template.md)).

That creates a collision with the cluster boundary:

- Cluster B is **Part 1 — local only**. Its exit criterion is "a typed, working
  application running locally. No Cloudflare services yet."
- Any real auth library needs **persistence**. Users, sessions, accounts and
  verification tokens have to live somewhere from the first sign-up.
- D1 is not provisioned until `REQ-D.1` in Cluster D, and `REQ-M.2` forbids
  jumping ahead to get it early.

So Cluster B needs a store that is not D1, without creating work that has to be
thrown away — and `REQ-D.1` names an exact path, `src/db/schema.ts`, written with
Drizzle, whose **first migration** is generated by `drizzle-kit generate` in
Cluster D.

Two questions had to be answered before writing a line of code:

1. Which auth library, and does it actually support both ends of this path?
2. What does it persist against now, and what exactly changes at Cluster D?

## Options considered

### The library

#### Option A — Auth.js (NextAuth v5)
- Pros: the best-known option; the course names it first; a Drizzle adapter
  exists.
- Cons: no first-party Cloudflare D1 story — D1 arrives via the Drizzle adapter
  plus community glue. Its session model is JWT-first, which pushes back toward
  hand-rolled decisions about token contents, exactly the anti-goal here.

#### Option B — Lucia
- Pros: named by the course; small; database-agnostic.
- Cons: **deprecated**. lucia-auth.com states outright: *"Lucia was deprecated in
  March 2025"*, and now ships a single-file `auth_session.ts` you are expected to
  copy into your own project. That is a *tutorial in hand-rolling auth* — the
  precise thing `REQ-B.5` forbids. Verified by fetching lucia-auth.com on
  2026-09-22.

#### Option C — Clerk
- Pros: genuinely a black box; nothing to persist locally.
- Cons: hosted third party, account + keys required, and it owns the user table —
  which breaks the Cluster D story, because Splitr's groups and expenses need to
  foreign-key onto users **in D1**. Also introduces a paid dependency into a
  course that specifies the free tier throughout.

#### Option D — Better Auth
- Pros: first-party Drizzle adapter (`@better-auth/drizzle-adapter`, published
  from the Better Auth monorepo) **and** first-party Cloudflare D1 support — a
  `D1Database` is an accepted `database` value in
  `@better-auth/core/types/init-options`, served by a built-in `D1SqliteDialect`
  in `@better-auth/kysely-adapter`. Both verified in `node_modules` at 1.7.5, not
  recalled. Email/password, sessions and CSRF are entirely inside the library.
- Cons: younger than Auth.js; the Drizzle adapter's table shape is dictated by
  the library, so `src/db/schema.ts` starts as generated code we then own.

### The Cluster B store

#### Option E — Better Auth's built-in Kysely + `better-sqlite3`, no Drizzle yet
Pass `database: new Database("./splitr.db")` and let Better Auth own the schema
via `npx @better-auth/cli migrate`.
- Pros: the shortest path to a working sign-up. Zero schema work in Cluster B.
- Cons: the schema then lives inside Better Auth's migrator, not in
  `src/db/schema.ts`. At Cluster D it has to be **re-expressed** in Drizzle and
  kept byte-compatible with what the library already created — a rewrite, and a
  second source of truth in the meantime.

#### Option F — Local D1 through Wrangler/Miniflare now
- Pros: identical runtime to production.
- Cons: that is Cloudflare, in Cluster B. It needs `wrangler.jsonc` and a
  binding, which `REQ-M.2` and the Part 1 exit criteria both rule out.

#### Option G — Local SQLite file, accessed through Drizzle, schema at `src/db/schema.ts`
- Pros: one schema definition for the whole project's life. Cluster D changes the
  *driver*, not the *schema*: `drizzle-orm/better-sqlite3` →
  `drizzle-orm/d1`. Both are the same SQLite dialect and the same
  `drizzle-orm/sqlite-core` table builders, and `drizzleAdapter`'s `provider`
  stays `"sqlite"` in both.
- Cons: Cluster B carries a native dependency (`better-sqlite3`) that production
  never uses; a local `.db` file has to be gitignored and recreated.

## Decision

We chose **Option D + Option G**: **Better Auth 1.7.5**, persisting to a local
SQLite file through **Drizzle 0.45.3**, with the schema at `src/db/schema.ts`
from day one.

Because: the deciding factor is that `src/db/schema.ts` should be **written once**.
`REQ-D.1` fixes that path, and Splitr's own tables will foreign-key onto Better
Auth's `user` table, so the auth tables and the domain tables have to be
expressible in the same file with the same tooling. Option E gets to a working
login faster but guarantees a translation step later, with a live database on the
other side of it. Option G pays the schema cost now, at the one moment when the
database is empty and getting it wrong is free.

**The tech lead's steer was "local SQLite via Drizzle now, same schema
throughout, swap the adapter at Cluster C/D." That is upheld — with one
correction.**

### The correction: `push` now, `generate` at Cluster D

`REQ-D.1`'s acceptance criteria say *"First migration generated by
`drizzle-kit generate`"*. If Cluster B generates migration files for the local
SQLite database, then Cluster D's "first migration" is not the first migration,
and the requirement is satisfied only by argument.

So Cluster B creates its local tables with **`drizzle-kit push`**, which
diffs the schema straight into the dev database and writes **no migration
files**. `drizzle/` stays empty until Cluster D, where `drizzle-kit generate`
produces migration `0000` from exactly the schema this ADR establishes — plus
whatever Splitr tables Cluster D adds. The local `.db` file is disposable dev
state, which is what `push` is for.

### What changes at Cluster D

Only the composition root. Concretely, in `src/db/index.ts`:

```ts
// Cluster B (now)
import { drizzle } from "drizzle-orm/better-sqlite3";
export const db = drizzle(new Database(DB_FILE), { schema });

// Cluster C/D (later)
import { drizzle } from "drizzle-orm/d1";
export const db = drizzle(env.DB, { schema });
```

`src/db/schema.ts` is untouched. `src/lib/auth.ts` keeps
`drizzleAdapter(db, { provider: "sqlite", schema })`. One caveat already
identified: D1 has no interactive transactions, so `drizzleAdapter`'s
`transaction` option must stay at its default `false` — verified in
`@better-auth/drizzle-adapter`'s `DrizzleAdapterConfig` typings. Because we never
switch it on, Cluster D inherits nothing to undo.

The fallback, if the Drizzle adapter ever proves awkward on D1, is that Better
Auth accepts a raw `D1Database` binding directly. We are **not** taking that
route, because it would move the auth tables out of `src/db/schema.ts` and
recreate Option E's two-sources-of-truth problem — but it is a real escape hatch
and worth knowing exists.

### Does starting a Drizzle schema now conflict with `REQ-D.1`?

No — it sets it up cleanly, provided the `push`/`generate` split above is
honoured:

| `REQ-D.1` criterion | Effect of this ADR |
|---|---|
| Schema lives at exactly `src/db/schema.ts` | Satisfied early, and never moved |
| Written with Drizzle | Yes, `drizzle-orm/sqlite-core` throughout |
| First migration generated by `drizzle-kit generate` | **Deliberately deferred** — Cluster B uses `push` so this stays genuinely first |
| Migration applied successfully | Cluster D |
| A D1 database is provisioned and bound | Cluster D |

## Consequences

- **Makes easy:** Splitr's own tables (`group`, `group_member`, `expense`,
  `line_item`, `settlement`) can foreign-key onto `user.id` the moment they are
  written, with no adapter translation. Cluster D becomes a binding change plus
  new tables, not a migration of existing ones.
- **Makes easy:** the Cluster B form's server-side validation can be exercised
  against a real database with a real session, locally, with no Cloudflare
  account in the loop.
- **Makes hard:** `better-sqlite3` is a native module. Anyone cloning the repo
  needs a toolchain that can install it (Docker image included —
  [ADR-0007](./0007-docker-for-local-development.md)). It must never be imported
  from code that also runs on Workers; it is confined to `src/db/index.ts`.
- **Makes hard:** two runtimes for the same schema means a D1-only constraint
  (no interactive transactions, statement limits) can pass locally and fail on
  D1. Mitigated by keeping `transaction: false` and by `REQ-D.6`'s explicit
  question about transaction-size limits.
- **Constraint to hold:** no migration files until Cluster D. If someone runs
  `drizzle-kit generate` early, `REQ-D.1` loses its evidence.
- **Revisit if:** Better Auth's Drizzle adapter turns out to misbehave on D1 at
  Cluster D (fall back to the native `D1Database` binding, and write the
  superseding ADR), or if Splitr needs a social provider whose secrets cannot be
  held locally.
