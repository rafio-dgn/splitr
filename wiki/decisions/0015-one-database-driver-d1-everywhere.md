# ADR-0015: One database driver: D1 everywhere, from Cluster C

- **Status:** Accepted. **Defect found on 2026-09-24:** §4's `--include-runtime=false` left every binding type undefined, so they were silently `any` (hidden by `skipLibCheck`). It's fixed by `cloudflare-globals.d.ts`, which gives global aliases of the importable `@cloudflare/workers-types` and doesn't clash with the DOM. See the CHANGELOG
- **Date:** 2026-09-23
- **Deciders:** Raffaele (timing: "provision D1 now, auth tables only"), AI (mechanism)
- **Requirement:** `REQ-C.1`, `REQ-B.5`, `REQ-D.1`, `REQ-M.2`
- **Amends:** [ADR-0009](./0009-better-auth-on-local-sqlite-via-drizzle.md), which put the D1 swap at Cluster D

## Context

`REQ-C.1` is "deploy the Cluster B app to Cloudflare". The Cluster B app
authenticates through Better Auth on `better-sqlite3`. That's a native Node module,
and it can't load on a V8 isolate. `src/db/index.ts` opened it at module scope,
`src/lib/auth.ts` imported that handle, and every gated page imports `auth`, so
without a Workers-compatible store no gated page can render in production.

ADR-0009 had planned the swap to D1 for Cluster D. Deploying in Cluster C
brought it forward, and Raffaele chose to provision D1 now for the four Better
Auth tables only. The domain tables still wait for `REQ-D.1`.

That left four questions about mechanism:

1. **Local development:** keep `better-sqlite3` locally and use D1 only when
   deployed, or use D1 in both places?
2. **Getting the handle:** a D1 binding only exists inside a request, but `db`
   and `auth` were module-scope constants.
3. **Creating the tables:** `REQ-D.1` requires the *first* migration to be
   generated by `drizzle-kit generate` in Cluster D.
4. **Types:** `wrangler types` output conflicted with the DOM lib.

## Options considered

### 1. Local driver

#### Option A: Two drivers, `better-sqlite3` locally and D1 deployed
- Pros: local development stays exactly as it was, including Docker.
- Cons: local verification would say nothing about the deployed store. This is
  the lesson of F-1, where curl passed while the browser failed ("verify in the
  medium the requirement names"). It keeps a native module and a C toolchain in
  the dev image, and needs a runtime switch in the composition root.

#### Option B: D1 everywhere, local D1 via Wrangler's platform proxy
- Pros: one driver and one dialect path. `initOpenNextCloudflareForDev()` in
  `next.config.ts` gives plain `next dev` the same `DB` binding, backed by a
  local D1 in `.wrangler/state`. The native module and the toolchain both go.
- Cons: `next dev` now starts workerd, and the container must run it. It does,
  verified below.

**Chosen: B.**

### 2. Handle acquisition

`getDb()` and `getAuth()` are async accessors that read the binding with
`getCloudflareContext({ async: true })`. That's the form that also works under
`next dev`. Each accessor keeps a `WeakMap` so the handle is built once per
binding per isolate, not once per request. Better Auth builds its route table
on construction, so rebuilding it per request would be pure waste. The change
touched exactly three consumers (`auth.ts`, `session.ts`, the auth route), and
ADR-0009's containment is why it stayed that small. The rejected alternative
was the synchronous `getCloudflareContext()`: it's only safe once a request is
genuinely in flight, and when it isn't, the failure only shows up in production.

### 3. Creating the tables

- `drizzle-kit push` against D1 needs `driver: "d1-http"` and a
  `CLOUDFLARE_API_TOKEN`, a second credential for a job the OAuth login
  already does. Rejected.
- `drizzle-kit generate` would spend `REQ-D.1`'s first migration. Rejected.
- **Chosen:** `drizzle-kit export --sql`, which diffs the schema against an
  empty database and prints DDL without writing a migration folder, applied
  with `wrangler d1 execute --local|--remote --file`. Scripts: `npm run db:local`
  and `npm run db:remote`. Known limit: they aren't re-runnable, because
  `CREATE TABLE` fails on existing tables. That's acceptable for four tables
  created once, and real migrations arrive at `REQ-D.1`.

### 4. Types

A default `wrangler types` includes the workerd runtime types. Those declare
HTMLRewriter's `Element`, which collides with the DOM lib that this app's client
components need. The first `tsc` after generating them failed in
`add-expense-form.tsx` (`HTMLSelectElement` not assignable to `HTMLElement`),
and it passed again with the file removed. **Chosen:**
`wrangler types --env-interface CloudflareEnv --include-runtime=false`
(`npm run cf:types`). It generates only the bindings, under the interface name
that OpenNext's `getCloudflareContext().env` already uses, so declaration
merging joins them without a bridge file or a cast.

## Decision

Splitr uses **D1 as its only database driver**, locally and deployed, from
Cluster C onward. Handles are acquired per request through `getDb()` and
`getAuth()`. The auth tables are created from `drizzle-kit export` DDL, and
`REQ-D.1`'s first generated migration stays unspent.

Because: two drivers would make every local check a statement about a database
we don't deploy. That's F-1's failure pattern built into the architecture.

## Consequences

- **Easy:** `REQ-D.1` adds tables to a database that already exists, is bound,
  and works in every run mode. `better-sqlite3`, `@types/better-sqlite3` and
  the dev image's `python3 make g++` block are gone.
- **Hard:** every data access is now async and request-scoped. There's no
  module-scope `db`, and there must never be one.
- **The deployed origin is configuration.** `BETTER_AUTH_URL` lives in
  `wrangler.jsonc` `vars`. It's a URL, not a secret. Local workerd
  (`npm run preview`) reads `vars` too, so it inherits the deployed origin and
  refuses its own localhost (403 `INVALID_ORIGIN`, measured). Locally,
  `.dev.vars` overrides it with an empty value. Wrangler does **not** read
  `.env` for this; that assumption was tested and failed. `next dev` doesn't
  read `vars`, so it's unaffected. `preview_urls` is `false` because a preview
  URL is a different origin and sign-in could never work there.
- **Revisit** at `REQ-D.1`, when `db:local` and `db:remote` give way to
  generated migrations.

## Verification

All on 2026-09-23:

- `tsc --noEmit` clean, `eslint` clean (after ignoring `.open-next/`,
  `.wrangler/`, and `worker-configuration.d.ts`), and `opennextjs-cloudflare
  build` succeeds with the same 15 routes as Cluster B.
- **Local workerd** (`preview`): sign-up returns 200 with an `Origin` header,
  and the gated `/groups` route returns 307 without the cookie and 200 with it.
  The row is in local D1.
- **`next dev` :3100:** sign-up returns 200, and the row is in local D1.
- **Container :3000:** rebuilt without the toolchain, and it signs in the user
  created on :3100. Both modes share one local D1 through the bind mount.
- **Deployed:** sign-up returns 200, the gated route returns 200 with the
  cookie, and a forged `Origin` returns 403. Before `BETTER_AUTH_URL` was set,
  the deployed sign-up returned 403 `INVALID_ORIGIN`, confirming the prediction.
  Test users were deleted from remote D1 afterwards.
