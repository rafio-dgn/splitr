# ADR-0026: The nightly sweep: `splitr-cron`, in-app reminders, backfill and re-index

- **Status:** Accepted
- **Date:** 2026-09-28
- **Deciders:** Raffaele, in structured questions on 2026-09-28 ("notifications in
  app is fine", then four choices). The AI proposed the options and recommended;
  he chose the recommendation on all four.
- **Requirement:** `REQ-E.6` (with `REQ-M.5`, `REQ-M.7`, `REQ-M.8`)
- **Builds on:** ADR-0016 §5 (the cron backfills `uncategorised`, never `other`),
  ADR-0025 §4 (the cron is the retry: it re-indexes missed expenses)

## Context

`REQ-E.6` asks for a `scheduled()` handler on a cron trigger, whose writes use
UPSERT-on-conflict, that gives **identical results when run twice**, and that
has a **manual trigger**. The brief gives it three jobs: settle-up reminders,
backfilling uncategorised line items, and (since ADR-0025) re-indexing
expenses whose search indexing failed. Splitr sends no email, so reminders
live in the app.

## Decisions

### 1. A fourth Worker, `splitr-cron`

It has a cron trigger, a D1 binding (read and write), and a **service binding
to `splitr-ai`** (`AiService`) for the backfill and the re-index. It has no
public URL (`workers_dev: false`) and carries `AI_SHARED_SECRET` like the app.

*Rejected:*
- inside `splitr-ai`, because it would need D1 writes, breaking ADR-0025 §5;
- inside `splitr-ledger`, because background jobs don't belong in the
  contested-write arbiter;
- inside the app, whose Worker is generated by OpenNext.

### 2. Reminders: an in-app banner once a debt is ≥ 3 days old

- **The cron UPSERTs one row per `(group_id, debtor_id, creditor_id)`**, with
  the amount and an `owed_since` date. On conflict, the amount updates and
  `owed_since` is kept. Pairs that no longer owe are deleted.
- **Who owes whom** comes from a new pure `suggestTransfers(balances)`: a
  deterministic greedy pairing (largest debtor with largest creditor, ties by
  id). Its first transfer is what the settle page already suggests. It's
  display only: it never moves money.
- **The banner** shows the *debtor* "You've owed Bob £40 since 12 Sep" on the
  group page and on the groups list, once `owed_since` is at least 3 days
  old. It disappears when the debt is settled, and there's no dismiss.
- **Known caveat:** if balances change so that the greedy pairing picks a
  different creditor, that pair is new, and its `owed_since` starts again.
- *Rejected:* a reminder for every debt the next day (noisier), and a dismiss
  button (more UI and a write path).

### 3. Re-index tracking: an `expense_indexed` table (not a column)

- **Raffaele chose precise tracking**: "an `indexed_at` column, set when
  indexing succeeds; the cron re-indexes what's missing". It's built as a
  **separate table** with the same meaning, because ADR-0018 §3 makes expense
  rows immutable (never updated; a mistake is voided and re-added). A column
  the app fills in after the save would be the first update to an expense row.
- **Migration 0002** creates `expense_indexed(expense_id PK, indexed_at)` and
  the `reminder` table.
- When `splitr-ai`'s `index` answers `ok`, the app UPSERTs the expense's row.
- The cron re-indexes expenses that have **no row** there (and aren't voided),
  **at most 50 per run**.
- **Existing rows:** the migration marks every expense that already exists as
  indexed (their vectors were written through the old path), so the first run
  doesn't re-embed history.
- *Rejected:* re-indexing everything nightly (the neurons grow with the data),
  and dropping re-indexing (it departs from ADR-0025 §4).

### 4. The manual trigger: `wrangler dev --remote --test-scheduled`

`npm run cron:run` starts the cron Worker in wrangler's remote mode, which runs
the real code on Cloudflare with the real bindings, and calls its local
`/__scheduled` endpoint. **No public endpoint is added anywhere.** It needs a
wrangler login, so it's Raffaele's to run on production. Locally, the same
script without `--remote` runs against the local D1.

*Rejected:* a secret-protected app route (a new public surface), and relying
on the dashboard (not scriptable for the demo).

## Idempotency: how "run twice, identical" holds

- **Deterministic keys:**
  - a reminder's primary key is `(group_id, debtor_id, creditor_id)`;
  - `owed_since` and `checked_on` are **dates** (`YYYY-MM-DD`, UTC), not
    timestamps, so a second run on the same day writes identical values.
- **The backfill only touches `uncategorised`**, and the re-index only touches
  expenses with no `expense_indexed` row. A second run finds nothing new, or retries only the
  items the first run failed on.
- **Vector upserts are keyed by id** (ADR-0022), so re-indexing twice leaves
  the same vectors.
- **The proof** (`scripts/verify/cron-twice.mjs`): snapshot the reminders,
  the category counts and the unindexed count after run 1 and after run 2, and
  they must be identical.

## Consequences

- There are now four Workers. The deploy order becomes ledger → AI → cron →
  migrations → app.
- **Raffaele sets one more secret:** `AI_SHARED_SECRET` on `splitr-cron`, with
  the same value as the app's.
- Each run costs a bounded number of neurons: at most 50 categorisations and
  50 re-indexes.
- `REQ-M.7` still holds: the cron runs off the request path entirely.
