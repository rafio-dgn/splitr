## The obstacle, and how it was handled

The first migration `CREATE`s the four auth tables, which already existed in
both databases, created in Cluster C from exported DDL (ADR-0015). Applying it
over them would have failed with "table already exists". The options were:

1. **Drop the auth tables, then apply the migration** (chosen). The migration
   history is then complete and true: every table exists *because of* a
   recorded migration.
2. Hand-edit the migration to `CREATE TABLE IF NOT EXISTS`. Rejected: it would
   be edited before it had ever run, and it would hide the state difference.
3. Insert a fake `d1_migrations` row and create only the domain tables by hand.
   Rejected: the recorded history would be a lie.

**Local D1** held only test accounts, which are disposable. **Remote D1** held
**one real account, Raffaele's own**, created on 2026-09-23 on the live site. I
found it by checking the row counts before dropping anything, and asked him
first. **He chose "drop it, I'll re-register"** over backup-and-restore. Both
databases were dropped and migrated.

## Constraints proved in the database, not just declared

Run against local D1 after the migration. Every refusal comes from SQLite
itself:

| Write | Result |
|---|---|
| 3 users, a group, an expense | accepted |
| A valid settlement A→B, recorded by A | accepted |
| Settle with yourself (A→A) | **refused**: `settlement_distinct_parties` |
| Recorded by a third member | **refused**: `settlement_recorded_by_party` (ADR-0018 §8) |
| Zero-amount expense | **refused**: `expense_amount_positive` |
| Category outside the closed list (`booze`) | **refused**: `line_item_category_known`. The list comes from `src/lib/categories.ts`, the same one the AI will use |
| Half a void (`voided_at` without `voided_by`) | **refused**: `expense_void_complete` |
| Delete a user who has records | **refused**: `FOREIGN KEY constraint failed` (every domain FK is `restrict`, because nothing in Splitr is ever deleted) |
