### REQ-D.2 — One piece of hot state in KV

**Statement:** Put one piece of hot, short-lived state in **KV**: a feature flag,
hot config, or a read-many cache such as the dashboard's "recent items".

**Acceptance criteria:**
- [ ] Exactly one such value lives in KV
- [ ] It is genuinely rebuildable if lost
- [ ] It is **not** primary data
- [ ] You can justify why it belongs in KV rather than D1

**Source:** capture §7 · **Status:** Not started (unblocked — [ADR-0004](../../decisions/0004-project-is-splitr.md))

**Notes:** The concepts list is pointed about this: *"stop reaching for KV by
default"*. Choosing something that would be a correctness bug if stale fails the
requirement even if it works.

### REQ-D.3 — R2 uploads via presigned URLs

**Statement:** **R2** uploads via presigned URLs: the Worker hands out a signed
URL, the client uploads directly, the Worker stores only the object key.

**Acceptance criteria:**
- [ ] The Worker issues a presigned URL
- [ ] The client uploads **directly to R2** — the file never passes through the
      Worker
- [ ] Only the object key is persisted
- [ ] You can explain why the upload bypasses the Worker

**Source:** capture §7 · **Status:** Not started (unblocked — [ADR-0004](../../decisions/0004-project-is-splitr.md))

**Notes:** ⚠️ This differs from EdgeLedger, which serves receipts *through* a
Worker route. The course requires the presigned-URL pattern. Do not copy the
EdgeLedger approach here.

### REQ-D.4 — Vectorize: embed, upsert, and a `/search` route

**Statement:** Embed each record with Workers AI (`@cf/baai/bge-base-en-v1.5`),
upsert the vectors into **Vectorize**, and ship a `/search` route that finds
records by meaning.

**Acceptance criteria:**
- [ ] Each record is embedded with `@cf/baai/bge-base-en-v1.5`
- [ ] Vectors upserted into a Vectorize index
- [ ] A `/search` route exists
- [ ] It returns results by **meaning**, demonstrably not keyword match

**Source:** capture §7 · **Status:** Not started (unblocked — [ADR-0004](../../decisions/0004-project-is-splitr.md))

**Notes:** ⚠️ EdgeLedger has Vectorize **switched off**. This is required here.
It is also the foundation for `REQ-E.4` (RAG) — the retrieval half of that
requirement is this index.

### REQ-D.5 — An unanticipated schema change

**Statement:** Make one schema change you didn't anticipate: add a column,
generate the migration, apply it, update the affected code paths.

**Acceptance criteria:**
- [ ] A column is added after the initial schema was settled
- [ ] A new migration is generated and applied
- [ ] Every affected code path is updated
- [ ] The original migration is **not** edited

**Source:** capture §7 · **Status:** Blocked on `REQ-D.1`

**Notes:** The exercise is migration discipline under change. Let the need arise
naturally rather than staging a fake one.

### REQ-D.6 — Answer the cluster questions

**Statement:** Be able to answer, unaided:
1. For each piece of data, why does it live where it does?
2. The D1 transaction-size limits: how did you avoid them?
3. Why doesn't your file upload pass through the Worker?

**Acceptance criteria:**
- [ ] All three answered without notes
- [ ] Q1 covers every store in use: D1, KV, R2, Vectorize

**Source:** capture §7 · **Status:** Not started

**Notes:** Q2 implies you will actually meet D1's transaction-size limits —
likely during the Vectorize backfill in `REQ-D.4`. Batch accordingly, and record
what the limit was and how you worked around it.

## Concepts to master

| Concept | What it gets you |
|---|---|
| D1: SQLite at the edge | Real relational queries close to the user; mind the transaction limits. |
| Drizzle on D1 | Type-safe queries and readable migrations, no deploy surprises. |
| KV: cache, eventual consistency | Use it for things you can rebuild; never for primary data. |
| R2: presigned URLs, zero egress | Hand file uploads off the Worker; pay nothing for bandwidth. |
| A decision framework | Stop reaching for KV by default; stop putting files in D1. |
| Vectorize: the fourth store | Search by meaning: store embeddings, query by similarity — the memory every LLM feature needs. |
